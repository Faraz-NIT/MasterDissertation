# 3. Language models as replenishment partners

## 3.1 What a language model brings to the process

A language model is useful here because replenishment information can be expressed in words. It can connect different ways of describing a rule to a consistent business meaning. A statement that a supplier ships cartons of six and a table headed carton size with the value six describe the same ordering condition. Recognising that relationship is distinct from calculating the quantity the store should buy. The model's potential contribution begins with interpretation, while the ordering calculation still depends on the stock, forecast and physical constraints.

The model produces its response using patterns learned during earlier training. In an instruction-following setting, those patterns are guided by the task description and the information supplied for the current decision. This can support flexible handling of ordinary language and tabular text. It does not give the model an automatic understanding of a retailer's internal conventions. A term such as available stock may have a particular meaning in one business and a different meaning in another. The task needs to state what the model is expected to identify or decide.

Qwen2.5-1.5B-Instruct is the pretrained model family used in the experiment. The model card describes an instruction-tuned language model with support for structured inputs and outputs (Qwen Team, 2024). The study uses the local Ollama tag qwen2.5:1.5b, in a compressed representation suitable for CPU inference. Its size is relevant to the research because it allows a substantial number of fresh calls within the available computing budget. The experiment examines this particular small model and configuration rather than treating its performance as representative of every language model.

A model card establishes what software is being used and how its publisher describes it. It does not establish the model's accuracy on the retailer's own messages. The study therefore evaluates the actual responses returned for the current supplier text and business context. It records those responses rather than relying on the model's general reputation. That distinction is useful to managers: choosing an established model family can be a reasonable starting point, but a credible adoption decision still needs evidence from the responsibilities assigned to it.

## 3.2 From a conversational assistant to a bounded agent role

The term agent can describe systems with very different degrees of freedom. Some can plan long sequences of actions, select among many tools and revise their approach after receiving feedback. Others perform a small role in a predefined workflow. The system studied in this dissertation belongs to the latter group. It uses three task-specific language-model calls within a fixed sequence. The agent roles do not independently change the retailer's budget, invent a supplier agreement or retrain the forecasting model.

The first role reads the supplier information. The second requests an approved planning tool and selects a permitted service priority. The third reviews the outcome of independent checks and gives an approval or a hold. These responsibilities are deliberately separated so that their behaviour can be examined. Each role has its own instructions and current inputs, but all use the same underlying Qwen model. The system is consequently a multiple-role agent workflow implemented through one model family, rather than a panel of independently trained specialists.

Yao et al. (2023) discuss the relationship between language-model reasoning and acting through external tools. Their ReAct work provides a useful conceptual reference for connecting a language model to actions whose consequences can be inspected. The present system is not a reproduction of the full ReAct method. It adopts the general idea of giving a model a defined interaction with tools, while limiting the sequence and available responses to suit a replenishment experiment that can be audited.

This limited arrangement is appropriate to the business question. Replenishment involves money, physical stock and service expectations, so flexibility needs to be connected to an explicit purpose. The model can interpret a message and route a request, while a numerical tool calculates a feasible plan. The process can then check whether the proposed order respects the current rules. Each responsibility remains visible. That makes it easier to investigate an error and explain the resulting business action than it would be in a system that allows every component to improvise its own policy.

## 3.3 Why numerical planning remains a separate responsibility

The ordering tool performs a different kind of work from the language model. It combines the forecast with on-hand stock, incoming deliveries and current ordering conditions. It considers carton sizes, minimum orders, supplier capacity and the daily budget. These requirements need to hold jointly across the portfolio. A plan that is suitable for one product may become unsuitable when considered with the other products competing for the same supplier capacity. Consistent arithmetic and constraint checking are therefore essential parts of the process.

Language models can assist with optimisation problems by connecting business questions to suitable numerical machinery. Li et al. (2023) explore this relationship in a supply-chain context. The useful distinction is between interpreting a request and solving the underlying constrained problem. A model can help express what the business wants or select an approved computation, while a solver applies the rules to the actual quantities. The experiment follows this division rather than asking the model to produce thirty order quantities directly from prose.

The separation also supports evaluation. If the agent-assisted system and the structured-data planner use the same numerical tool, differences can be examined in relation to the language-model layer. If they instead used different tools and forecasts, a performance gap would be harder to interpret. It could reflect any of those changes. Keeping the shared numerical capability visible allows the study to ask a more precise question about the additional roles than a comparison of two entirely different systems would permit.

This does not make the numerical planner infallible. It operates on a forecast, a defined cost preference and a limited planning horizon. Its assumptions may be unsuitable for a particular retailer. A feasible plan can still produce a shortage because demand is uncertain or a delivery is delayed. The important point is that the numerical component has an explicit responsibility and can be examined on that basis. The language model's interpretation, the planner's quantity decision and the physical outcome are retained as related but separately inspectable stages.

## 3.4 The supplier-reading role

The supplier-reading role has a concrete task: extract the current ordering conditions without changing their meaning. For each of the three synthetic supplier groups, it identifies carton size, minimum order, delivery days and dispatch capacity. It also extracts the current daily budget. This gives thirteen numerical fields for each supplier-reading call. Supplier identity and coverage matter as well, because a correct value assigned to the wrong supplier would still provide the planner with an incorrect rule.

The messages use three controlled formats. The prose format describes the conditions in a consistent sequence. The memo format changes the order in which quantities appear. The table format places the fields under headings. These formats test whether the model connects a number to its meaning rather than simply copying numbers in the order they appear. A capacity of ninety-seven units, for example, needs to remain a dispatch limit even when it is the first number in a sentence that later mentions a carton of three.

The extraction is checked against the authenticated current contract fields represented by the message. A disagreement produces a hold rather than a corrected response or a substituted conventional order. This gives the experimental workflow a clear treatment of failure. The model's answer is preserved, its accuracy is scored and the proposal is not released through an alternative policy. The system does not quietly remove an interpretation error from the evidence by replacing it with a successful result from another component.

The controlled source has limits. It does not contain ambiguous attachments, conflicting negotiation histories or unrestricted commercial legal language. A good extraction result therefore supports the task actually tested. It gives a reason to investigate a language interface for supplier rules, but it does not establish that every supplier communication can be handled without review. The dissertation retains that distinction when interpreting the reading accuracy. Managers should ask whether their own document variation is similar to, narrower than or broader than the variation represented by this experimental corpus.

## 3.5 The coordination role and business priorities

The coordination role connects a current business situation to the approved planning process. It is instructed to request the constrained-order tool. For routine trading and supplier disruption, the expected priority is balanced. For an active announced promotion, the expected priority gives additional weight to service. This is a defined business-policy mapping within the experiment. The language model does not choose a new objective for the retailer or assign its own commercial value to every customer shortage.

The role receives the current scenario, whether a promotion is active, aggregate stock, the current forecast and the verified supplier information. These inputs describe the decision as it appears to the coordination role. They do not include realised future demand. The tool then uses the chosen priority with the full portfolio state to calculate quantities. This arrangement allows a routing or priority-selection error to affect the proposed plan in a visible way, rather than being reduced to an isolated classification score without an operational consequence.

An important distinction arises between a permitted response and the correct policy response. The role can select a priority that is recognised by the system yet inconsistent with the instruction for that situation. A valid field therefore does not guarantee a correct choice. The order may still respect the supplier and spending limits, so a physical constraint check alone will not reveal the semantic error. Measuring priority selection separately is necessary to understand how the model followed the business instruction.

This is a useful management lesson even before considering the empirical findings. Organisations often combine policy statements with numerical systems. A phrase such as protect availability during the promotion needs a defined relationship with the planning mode. If that relationship is left unclear, a system can produce technically acceptable actions that differ from the intended business response. The experiment makes the expected mapping explicit and retains the model's actual choice, allowing the study to assess interpretation of policy as well as interpretation of supplier numbers.

## 3.6 Review and the authority to execute

The review role receives the results of independent checks on the proposal. It considers whether source verification passed, the approved tool was requested, the solver produced a feasible proposal and the proposed quantities passed the listed action checks. It then returns an approval or a hold. This makes review a visible stage in the workflow. The model is asked to apply a stated release rule, rather than infer permission from the tone of a supplier message or the confidence of another agent role.

The final execution gate remains deterministic. The gate only permits release when the required conditions pass and the review role approves. This means the language model cannot override a failed budget or supplier check. It also means that an approval from the model is not itself the complete authority to buy. The release process combines the model's review with conditions imposed outside the model. This is how the system maintains the distinction between proposing an action and being permitted to execute it.

Parasuraman et al. (2000) describe different functions and levels of automation. Their framework is helpful because a retailer can automate information processing without granting unrestricted authority over implementation. The supplier-reading role, the planning tool and the release gate have different functions in that arrangement. Parasuraman and Riley (1997) also draw attention to how people use or misuse automation. These contributions support a process view in which the manager needs to understand what each automated component is authorised to do.

The study does not claim that review by a language model is a substitute for a retailer's governance. The independent numerical checks already perform substantial work. In the completed main experiment, the review task largely involved proposals whose checks passed. The absence of false approvals in those cases does not establish how well the review role would detect a broad range of deliberately unsafe plans. Those conditions were outside the requested clean study. The empirical interpretation therefore centres on the observed guarded workflow rather than an unrestricted promise of model judgement.

## 3.7 Instructions, development and stable evaluation

The task instructions supplied to a language model are often called prompts. In this study, they state the responsibility of each role and the permitted response format. The supplier role is told how to connect each number to its field. The coordinator is told how to request the approved tool and choose the business priority. The review role is told when to approve and when to hold. These instructions are part of the experimental system because changing them can change the behaviour being evaluated.

Development checks were conducted before the protocol was frozen. The first round exposed a field-swapping error and a review error. Small worked examples were then added to clarify the intended reading and review rules. This was task configuration, not training of the model's weights. The development records were retained separately, and they were not counted as primary evaluation results. This distinction gives the researcher a legitimate opportunity to make the system functional while preserving an honest account of what was discovered during development.

Once the protocol was frozen, the study used the same instructions, examples, model settings and evaluated policy code throughout the complete grid. It did not revise the prompts after examining the primary outcomes. There were no retries of a failed answer, no cached-response substitution and no evaluation-time repair. Fresh native Ollama responses were saved for every role call. That procedure makes the primary findings evidence about the frozen system rather than evidence about an evolving collection of responses selected because they happened to work.

Stable evaluation is especially important for a system with several roles. If a poor coordination result led to a new instruction halfway through the study, earlier and later seeds would no longer evaluate the same process. A larger call count would then provide a misleading appearance of consistency. Hevner et al. (2004) emphasise evaluation within design-science research. The present study responds by separating development from the registered evaluation and by preserving both the unsuccessful development cases and the complete primary decision records.

## 3.8 A strong comparison and a credible contribution

The structured-data planner is the main test of the language-model layer. It receives the current rules in organised fields and applies the same numerical planning tool, stock-age projection and scenario-priority mapping used by the agent workflow. Its inputs describe an idealised information state. This makes it a stronger comparison than a simple ordering rule, because it removes the need for the additional interpretation and coordination calls while retaining the planning capability.

The comparison addresses a common problem in assessing technology packages. Several improvements can be introduced at once, then the outcome can be attributed to the component that is most novel or visible. In this case, the language model is visible because it reads text and acts through named roles. The numerical tool may be less visible to a business audience, yet it can account for much of the performance difference against conventional ordering. Comparing the agents with the same tool makes that contribution observable.

The possible business value of language remains important. A retailer that already has perfect structured supplier fields may gain little from reading those same fields through a model. A retailer whose information arrives in varied text may face a different operating cost. However, the experiment does not measure the staff effort needed to create the structured inputs, the rate of manual errors or the work needed to review a model's output. Those are potential sources of incremental value that should be assessed in a later operational pilot.

The most credible contribution from this study is consequently a measured statement about the responsibilities actually assigned to the model. The experiment can show whether supplier interpretation worked in the controlled formats, whether policy choices followed instructions and whether the combined process met the declared operational goals. It can also show whether those outcomes changed when the numerical tool operated without the language-model roles. This is a practical basis for discussing agent-assisted replenishment without treating a useful language interface as proof that the model independently optimises inventory better.
